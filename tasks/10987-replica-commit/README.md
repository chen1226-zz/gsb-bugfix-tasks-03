# 10987 · 复制日志提交索引（replica）

`replica.py` 在单进程内模拟三节点复制日志，网络丢包可注入。

接口：`Replica(nodes, rng, drop_rate)` 的 `.append(command)` / `.elect_leader()` /
`.ack_count(command)` / `.committed()`。

| 文件 | 说明 |
| --- | --- |
| `replica.py` | 已修复的模块（Raft 提交规则） |
| `chaos.py` | 复现脚本：200 组随机丢包 + 随机换主 |
| `tests/test_replica.py` | unittest 用例 |

## 原 bug

旧实现有两处致命问题：

1. `append` 不等多数派确认就把条目标记为已提交（`commit_index` 直接推进）；
2. `elect_leader` 直接把比新主长的跟随者日志截断，已提交条目随换主被删除。

两者叠加，客户端看到的已提交历史在选举后回退。

## 修复后的提交规则（Raft）

1. **多数派提交**：条目被复制到多数派（> n/2）后才允许提交；
2. **只提交当前任期**：领导者仅依据「当前任期」条目的多数派复制直接推进
   `commit_index`，旧任期条目只能随新条目间接提交——防止任期交叉时把
   仍可能被覆盖的旧条目误判为已提交（Raft 论文 Figure 8 的情形）；
3. **任期比较 + 日志匹配**：每条日志携带写入时的任期；选举时选民只把票投给
   日志至少与自己一样新的候选者（按 `(末条任期, 末条下标)` 字典序比较），
   保证新领导者拥有全部已提交条目（领导者完备性）；
4. **复制即修复**：AppendEntries 找到最长一致前缀，截断跟随者分歧后缀再追加；
   已提交条目必然在新主日志的相同下标处，因此永远不会被覆盖或删除；
5. **换主继承提交水位**：新主上任时继承旧主的 `commit_index`，
   客户端读不到已提交历史的回退。

## 状态机

节点角色状态机：

```
                 选举超时 / elect_leader()
        ┌────────────────────────────────┐
        ▼                                │
  ┌───────────┐   赢得多数派投票    ┌─────────┐
  │ CANDIDATE │ ──────────────────▶ │ LEADER  │
  │ term += 1 │                     │         │
  └───────────┘                     └────┬────┘
        │                                │ AppendEntries（丢包可注入）
        │ 落选（日志过旧，               ▼
        │ 改选日志最新者）          ┌──────────┐
        └─────────────────────────▶ │ FOLLOWER │
                                    └──────────┘
```

单条日志的提交状态机：

```
   append           复制到多数派            当前任期条目
 ┌────────┐  ┌──────────────────┐  ┌────────────────┐  ┌───────────┐
 │ 已写入  │─▶│ 已复制到多数派    │─▶│ 已提交          │─▶│ 可读/已应用│
 │ 领导者  │  │ （旧任期条目到此   │  │ commit_index   │  │ committed()│
 └────────┘  │  为止，不算提交）  │  │ 推进，前缀生效  │  │ 返回前缀   │
             └──────────────────┘  └────────────────┘  └───────────┘
        未提交条目可能被后续选举覆盖；已提交条目保证：
        存在于多数派、出现在所有未来领导者日志中、永不回退。
```
